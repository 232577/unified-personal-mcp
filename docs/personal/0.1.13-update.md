# 0.1.13 升级与断线排查

## 已有 0.1.10、0.1.11、0.1.12

从本项目 GitHub Releases 下载 `UnifiedPersonalMCP-0.1.13-source-update.zip` 及其 SHA256 文件。核对下载摘要后，将 ZIP 解压到旧安装目录之外，例如下载目录。不要覆盖旧包，不要把升级文件放进旧包，也不要复制旧设备的隧道密钥给另一台设备。

运行 `update.cmd`。它寻找已登记的安装；不能唯一确定时，要求输入原完整包目录。程序校验升级文件、原包清单、固定依赖与浏览器/搜索/隧道资源，然后在原目录旁创建 `UnifiedPersonalMCP-0.1.13`。任何校验失败都保留旧包和当前服务。目录已存在时拒绝覆盖；先阅读上一次结果，不要重复强行安装。

准备新目录不等于运行新版本。受控切换使用新目录中的 `scripts/switch_managed_release.py`，只控制当前用户已有的管理型自启动任务，并保留原登记用于失败回退。必须没有其他活动工作流；遇到忙碌或未知资源先完成原任务，不强杀。切换会短暂断线。

切换后通过对应设备的插件读取 `server_info`：应返回 `version=0.1.13`，完整配置为 58 工具，健康状态正常。随后实际执行一次工作流创建、文件读取、命令观察和结束，才完成远程验收。若客户端缓存旧工具描述，刷新该插件工具目录后使用新聊天。

## 重启后为什么离线

0.1.10 已有登录自启动：当前 Windows 用户登录后延迟约 20 秒启动，依赖完整包原路径、该用户的本地配置及联网能力。它不是未登录时运行的系统服务。平台的“超过 300 秒未见 tunnel-client”仅说明隧道离线，不能证明具体原因。

1. 登录部署时使用的 Windows 账号，打开原目录的 `UnifiedPersonalMCP.exe`，查看运行版本和连接状态。
2. 检查“登录自启动”是否启用。若移动过目录或只复制了 EXE，恢复完整安装路径，重新启用自启动。
3. 若服务在运行但 OpenAI 未连接，查看本机网络及代理是否已启动，再使用“连接 OpenAI”重试。0.1.11 起支持读取显式 Windows 系统代理；本次更新包含这项修复。不修改防火墙或关闭安全设置。
4. 若双击无窗口，运行原包 `启动诊断.cmd`，读取 `%LOCALAPPDATA%\UnifiedPersonalMCP\diagnostics\startup-latest.json`；不要提交密钥文件。
5. 本地控制台恢复连接后，再由客户端重读服务版本和执行真实调用。离线设备不能仅凭本机源码更新被宣称已更新。

## 新设备与公开发行边界

源码升级 ZIP 只包含本项目和可再分发的上游源码、脚本、文档与资源摘要，复用旧设备已有的完整运行环境。它不是独立安装包。全新设备可按 [构建说明](构建说明.md) 从各组件官方来源安装，或由同一所有者迁移其个人完整运行包，再设置该设备独立的隧道。

当前 Windows-MCP 依赖含 GPL 组件；本次不公开再分发组装后的第三方二进制集合，也不宣称其组合许可问题已解决。个人完整包保存在本机，公开仓库和升级包排除配置、运行 key、状态数据库、浏览器资料和业务数据。

## 安全拒绝的区别

软件错误导致的错误权限响应、参数误解析、只读工具副作用需要修复。跨工作流操作、未知结果重放、忙碌时更新、未授权凭据与真实破坏操作的拒绝必须保留。工具注解和本地 full_control 配置都不能保证平台审批通过；没有重新包装、改名或换连接来重放被平台拒绝的操作。
