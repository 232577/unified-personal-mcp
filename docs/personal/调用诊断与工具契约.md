# 调用诊断与工具契约

当前候选目录已增加到 53 个工具，包含 command_status；统一错误输出分支、回执隔离和中文检索修复见[工具失败隔离与结果观察](工具失败隔离.md)。下文 52 工具内容保留为上一阶段的迁移说明，不能作为当前已部署数量。

本次开发针对调用可观测性与契约清晰度，不是关闭或绕过平台安全检查。
源码更新不会自动切换运行服务；必须区分源码提交、运行版本、工具目录和真实调用结果。

## 本地证据位置

新版运行时在当前安装的私有 `data_root/diagnostics/` 写入以下文件，不上传外部分析服务：

- `catalog.json`：本实例实际 `tools/list` 所用的完整工具定义与指纹，不包含运行密钥或工作流令牌。
- `calls.jsonl`：当前分阶段调用记录。
- `calls.1.jsonl` 至 `calls.3.jsonl`：滚动保留的旧记录；默认每份不超过 1 MiB。

目录指纹现在覆盖完整公开 descriptor，包括 description、title、schema、annotations 和后续扩展元数据。
`catalog_revision_format=complete-descriptors-v2` 用于区别旧的部分字段算法；仅算法升级也会改变指纹，不能把它误判为平台缓存故障。
比对指纹时还必须核对权限模式、启用能力和资源配置；例如隔离测试 trusted 与生产 full_control 的工具描述可能不同，不能直接要求两个目录散列相同。
`catalog.json` 代表当前启动实例；更新服务前应保留需要复核的旧快照。诊断记录有界且会轮转，不是永久执行账本。

## 阶段的确切含义

| 阶段 | 含义与边界 |
|---|---|
| `http_received` | 本地 HTTP POST 处理函数已开始，HTTP 请求头已经由服务器解析；不是云端入口日志 |
| `tool_received` | 请求进入工具运行时；尚未证明参数或授权通过 |
| `tool_validated` | 输入 schema 校验通过；不等于业务权限或工作流归属校验通过 |
| `tool_returned` | 工具运行时已返回结果；`outcome=ok` 是工具结果级状态，不等于命令退出 0 或业务验收成功 |
| `tool_raised` | 调用以异常结束；不凭此推断副作用没有发生 |
| `http_finished` | 本地 POST 处理函数正常返回；记录真实 HTTP 状态，不证明隧道或 ChatGPT 已接收 |
| `http_failed` | POST 处理出现异常；不自动重试，也不推断已经执行的操作可以重放 |

同一次 HTTP 调用及其工具阶段使用服务端生成的 `trace_id`，直接运行时调用各自生成新的关联标识。
`instance_id`、递增 `sequence`、UTC 时间、耗时、目录指纹用于区分实例和时间段。
只记录已公布工具名、schema 中已声明的有限 action、已知错误代码，以及命令结果实际提供的退出码和运行状态。
不记录调用参数、结果正文、文件内容、环境变量、请求 URL、请求头、JSON-RPC id、调用方 request_id 或 workflow_id。
原始 HTTP request-line 日志被上述结构化记录替代，避免查询串中的秘密进入访问日志。

GET、请求头解析之前的连接失败、隧道内部和平台安全检查不在这份日志的覆盖范围内。
因此“没有找到记录”不能独立证明平台故障；还需核对实例、时间、日志覆盖和丢失状态。

## 日志失败与恢复

`server_info.diagnostics` 提供 `catalog_available`、`dropped_events`、`rotations` 和保留上限。
日志写入失败不会改变原工具结果，也不会再执行一次操作；本实例丢失计数保持可见，不能被下一次成功写入清零。
这里的记录不能替代 `OperationStatus`、工作流凭据代次与业务数据复核。发生未知结果时仍遵循原请求去重规则。
诊断是同步的有界本地写入，不承诺磁盘故障下的实时性或完整投递。

## 测试与上线边界

自动测试使用隔离配置、临时目录和本地 HTTP 端口，不连接或重启生产隧道。
真实截图测试 `tests_bf/browser/test_frame_privacy.py` 按用户要求不执行；其他图像契约测试只使用合成夹具，不作为截图证据。
不执行桌面验收脚本、截图流程、批量重放或面向 ChatGPT 的限流探测。

本地测试通过只能证明这些已覆盖行为。是否消除用户遇到的平台提示，必须在后续明确批准的部署与真实调用中另行验证。

## 独立只读工作流查询（开发分支）

本分支保留原 50 个工具的调用兼容，新增两个工具，总数 52。旧 `UnifiedTask` 仍按混合写入工具声明；没有把其 begin/end/resume 等操作标为只读。

| 工具 | 输入 | 行为 |
|---|---|---|
| `workflow_list` | 空对象 `{}` | 列出当前认证所有者尚未结束的工作流；不要求先创建工作流，不返回秘密令牌 |
| `workflow_status` | 当前有效的 `workflow_id` | 返回同一所有者的工作流状态及活动工作流的受管命令/进程诊断；不续租、不激活、不轮换凭据、不结束资源 |

两者采用固定、独立 schema，拒绝额外 action、principal、project_path 或注入参数。注解为 readOnly=true、destructive=false、idempotent=true、openWorld=false，表示观察有限的已归属运行记录，不访问任意外部系统。
日志和在途计数属于内部观测/资源保护，不改变业务工作流状态、租期或凭据。状态查询仍需原有归属和有效凭据校验，不因只读而省略认证。过期代次凭据被拒绝；非活动状态仅被观察，不被隐式恢复。

旧 `UnifiedTask list/status` 与新入口共享相同底层实现并保持相同结果。旧接口保留是兼容迁移措施，不是已经完成所有生命周期 API 拆分。后续移除旧查询动作或拆分其余状态变更入口，需要先验证客户端迁移；本次不强制破坏现有客户端。

### 客户端迁移步骤

更新前确认所有相关工作流的实际资源，选择明确允许的维护时机。不要为升级终止无关工作流或直接重启宿主。本次源码提交没有执行生产升级。
运行新版并刷新客户端工具目录后，先核对 `server_info` 的工具数量、完整目录指纹及诊断字段，再使用独立的查询工具。当前仅见 50 个工具时，不能直接假设新版入口已存在；旧接口继续适用。
begin/activate/resume/end 仍按旧调用方式执行；恢复时先查真实列表，使用实际 credential_generation，不复用历史秘密凭据。

## 运行时授权与标注分离（2026-10-09 开发变更）

服务端现在从 `tool_policy.py` 的明确策略决定是否需要工作流写权限，以及是否走既有请求去重账本。工具目录中的 readOnlyHint 只描述行为，不能改变这条准入路径；新增工具必须先登记策略。

目录在 Runtime 资源初始化前进行契约校验。不完整的描述、无效 schema、缺失或非布尔风险标注、与已登记读写行为不一致的标注会拒绝启动，而不是静默替换为只读或向客户端发布。该校验是约定检查，不是所有工具副作用的自动安全证明。

本轮纠正了三类低估效果的标注：非空 write_stdin 可触发受管命令的破坏性/外部效果；Clipboard set 会覆盖共享剪贴板；full_control 模式中的 read_file、list_dir、list_files、search_text、apply_patch、view_image 允许项目之外的路径，因此标注为 openWorld。trusted/safe 的原有项目范围不变。运行权限没有扩大，这些修正可能增加确认，不保证任何具体调用获准。

### 发布阻塞与验收

本次用户报告的安全提示仍须进行部署后的真实验收，不能因修复插件问题就自动关闭。至少核实当前运行代码/目录、只读查询、隔离项目的合法文件修改与测试执行、拒绝情况下零额外副作用和正常工作流清理。操作必须使用真实返回的凭据与命令标识；不恢复或重放先前被拒绝的操作来试探检查。

如果候选版仍返回同一安全提示，保留原文与受控诊断，标记该验收失败或未完成，不提高权限、不隐藏能力，也不将安装或源码完成写成故障已解决。平台是否放行与本地工具调用是否正确是两项不同结论。
