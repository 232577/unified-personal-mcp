# Unified Personal MCP 远程开发完整性升级方案

状态：2026-09-22 用户已确认完整方案，进入实施；本文件不代表功能已经实现。

## 用户目标与既有约束

同一份 Windows 程序通过 OpenAI 隧道连接机主自己的开发机，换机后使用配置复用。多个项目能同时开发；自动化命令在后台运行；中断后能在原对话继续；开机登录后连接；代码公开。权限继续使用已授权的 full_control，实际能力受当前 Windows 用户权限约束。

保留现有代码、桌面、Chromium、WebView2 组合及项目默认目录模型。保留正在运行的业务程序、原 BF/coding 服务和已有密钥。开发和故障注入只在隔离环境执行。正式切换遵循用户的切换时机，不能把“包已构建”写成“当前服务已启用”。

当前基线：源码 0.1.3，49 个工具，完整专项回归 348 项通过；本机真实插件仍返回 0.1.2。0.1.3 已完成包验证并设置为下一次登录启动目标。本轮设计不修改这些运行状态。

## 已确认的缺口

以下由源码及此前实际使用记录证实；没有为了验证故障而中断生产。

| 优先级 | 缺口与用户影响 | 证据入口 |
| --- | --- | --- |
| P1 | 隧道进程运行后退出，主服务仍活着，计划任务不会重启它，远程无法自行恢复 | personal_mcp/service.py 的 _maintain；tunnel.py 的 ready |
| P1 | BF 内部客户端退出后，后续调用持续失败；重开对话也不修复服务端连接 | personal_mcp/bf/executor.py 的 _thread_main/call |
| P1 | 等候超时被记为永久 unknown，即使后台操作稍后完成，也没有通用结果查询入口 | personal_mcp/operations.py；bf/executor.py 的 finished 回调 |
| P1 | 工作流令牌丢失且原命令仍运行时，既不能继续使用，也不能安全回收 | personal_mcp/workflows.py 的 begin/list/release_idle |
| P1/P2 | 慢项目初始化持有全局锁；同工作流长轮询会挡住查询和取消 | workflows.py 的 activate/use |
| P2 | 只知道服务版本，不知道组件状态、资源使用量或工具目录是否过期 | host.py 的 server_info；catalog.py |
| P2 | 换机自启动仍依赖源码目录脚本，便携包未包含完整安装入口 | scripts/build_portable.py；install-autostart.ps1；gui.py |

“每工作流 16 条命令”是进程容量，不等于 16 个工具请求可同时通行。共享桌面前台输入仍只能串行。同一工作目录的同时写入继续要求独立副本或明确协调，增加线程不能消除文件和端口冲突。

当前官方 Tasks 与连接协议已演进，直接照搬旧教程的接口会制造新的不兼容。Inspector 的当前主线也已到 v2，应固定版本和 Node 要求后使用，不把 latest 无条件装进运行包。此次只学习协议与架构，不直接复制未审查的新代码；如后续复用源码，记录提交和许可证。

## 路线选择

1. **推荐：在现有体系补完整生命周期。** 逐步补齐连接恢复、操作结果、工作流接续、并发控制和安装验收。每个阶段独立可交付，兼容现有客户端。
2. 仅继续修零散提示和增加并发额度：改动小，但令牌丢失、连接退出和未知结果仍会造成阻塞。
3. 换框架并全面升级协议：接口变更大，现有客户端和 Windows 进程归属需要重新验证，不能直接解决已有的业务状态管理缺口。

选择路线 1。版本按三个交付单元推进；一项未验收不阻塞无依赖项的开发，但未验收项不得出现在功能已完成清单。

## A：组件健康与恢复（目标 0.1.4）

### 健康输出

`server_info` 保留现有输入和字段，在输出中增加 `health`、`catalog_revision` 与 `resource_usage`。`ok` 继续表示本次查询成功，组件好坏由 `health.status` 明确表示，不能把 `ok:true` 当成所有功能正常。

组件状态为 `healthy / degraded / recovering / stopped`，未启用隧道为 `disabled`；报告最近成功时间、最近错误代码、恢复次数、下次重试时间。只返回标准错误代码和受管资源计数，不返回密钥、完整环境变量、日志原文或所有者之外的信息。健康查询读取已缓存状态，不能等待网络探测或业务工作流锁。

工具目录指纹来自规范化的工具名称、参数与输出 schema、注解，排除设备路径和运行时随机数据。用它识别不同版本目录；它不能强迫 OpenAI 客户端自动刷新。发布验收必须包含真实插件对新增接口的调用。

### 隧道监督

独立监督线程负责调度和有界健康观测，单独恢复执行单元执行启动/健康等待；不能依赖可能等待工作流清理的维护线程，也不能把健康查询阻塞 30 秒。确认自有隧道进程退出后，释放其 Job/锁并按 1、2、4、8、16、30 秒上限的退避重建，含小幅抖动；持续健康后重置退避。

子进程仍存活但 /readyz 暂时失败时先标 degraded，允许隧道客户端自己的网络重连，不按一次探测失败强杀。二进制校验失败、凭证缺失或隧道所有权不明时报告需处理的故障，不无限高速重试。配置修复后的明确连接请求可以重新触发检查。

登录启动时网络尚未就绪，也保留已启动的本地服务并进入上述监督流程；不能因为首次隧道连接失败而拆除整个服务。初始化前校验失败仍准确报告配置错误。将“已创建进程”和“隧道可用”分成状态，不能把仍存活但尚未 ready 的客户端当成已退出而重复启动。

同时只能存在一个连接尝试。停止信号先禁止新尝试，再等待本轮恢复有限结束，回收只属于本安装的资源。自动恢复不得启动第二个同 ID 隧道，不接触旧 BF 隧道。

### BF 内部连接

为 BFExecutor 增加连接代次和独立状态锁。只有旧客户端线程已确定退出、原已分发 Future 已归档后，才对同一个 BF server 重建 Client；不重建 TaskStore、浏览器管理器或业务程序。

新请求可以等待一次有界连接恢复；恢复期间返回明确可恢复状态。并发请求共享一次恢复，不各建一条连接。已经分发的调用绝不重新提交；已确认结果归档，不能确认的保留 unknown。活着但疑似卡住的旧线程只报告 degraded，不与新线程竞争控制同一组资源。

固定版本的 FastMCP 内存连接会进入和退出 server lifespan，必须用真实依赖验证跨代次生命周期。若连接退出会清理业务资源，先将资源所有权移至主服务生命周期；不能仅复用 server 对象就宣称 PID 保持不变。Future 已完成或取消不等于原生副作用已停止，资源占用仍以真实管理器证据判断。旧代次回调只能结算自己已分发的操作，不能改写新代次健康；明确关闭为终态，不触发重连。

### A 的验收

- 自有假隧道异常退出后恢复成功，原编码命令和应用 PID 不变。
- 网络探测失败但进程活着时不重复启动隧道；修复网络后健康状态恢复。
- 模拟登录时离线，网络恢复后自动连接，本地服务与原工作流不重建。
- 密钥缺失、二进制损坏、端口/隧道占用分别返回可区分诊断，无密钥泄露。
- BF Client 被故障注入终止后新调用可恢复，先前写动作计数仍为一次。
- 真实固定版 FastMCP 连续两次连接代次成功，旧 lifespan 完整退出，TaskStore/BrowserManager 身份与原受管 PID 保持不变。
- 多个并发请求只产生一个重连；停止过程中不会又拉起组件。
- 真实无控制台 pythonw 父进程运行恢复流程，控制台窗口句柄为 0。

## B：中断后的接续与并发控制（目标 0.1.5）

### 操作状态与迟到结果

增加只读 `OperationStatus` 工具，以合法 workflow_id 和 request_id 查询；返回操作名、`running / completed / failed / unknown`、更新时间与最终结果引用。原始参数摘要用于冲突检查，但不暴露参数原文。保留既有操作 ID 的幂等契约。

客户端等候超时与执行状态分离。BF Future 继续运行时记 running，完成回调持久化其真实结果；响应丢失后可查询，不能重复操作。超过结果大小上限时保存已完成状态及有界摘要/私有结果引用，不因为输出过大误称执行未知。主服务崩溃后没有活证据的 dispatched 状态仍为 unknown。

状态更新使用事务和条件更新，完成回调可以将 running 或本次已分发操作的 unknown 收敛为可验证的最终结果。等候超时只能在尚未完成时更新等待信息，不能把已完成状态倒退；完成、超时和服务关闭同时发生的顺序必须纳入测试。只有明确执行失败才能写 failed，异常本身不能证明写操作未发生。

BrowserActionStatus 等现有专用查询继续可用，逐步适配统一结果，不破坏旧接口。查询在控制通道执行，不排到长时间写请求后面。结果保留时间、容量和淘汰规则公开于诊断，日志和结果不无限增长。

### 工作流接续

增加显式 `UnifiedTask resume`，输入 workflow_ref、request_id、expected_generation；list/status 增加 credential_generation 供调用者读取。仅当前已认证所有者可使用；普通 begin、PROJECT_BUSY 或自动重试不能隐式接管。工具描述必须要求确认是在继续同一个项目的工作。仅 ACTIVE 工作流可接续；其余状态返回明确诊断，不能通过接续复活已结束或清理失败的资源。

将稳定资源标识与访问凭证分开：现有 token_hash 作为兼容的稳定资源键，新凭证映射到它；操作记录、command_id、BF token 与现有 Job 不变。增量凭证表记录当前代次及撤销状态，避免旧令牌通过兼容分支重新生效。

接续在工作流控制门内原子轮换凭证。已分发操作继续完成，新提交使用新凭证，旧凭证得到明确 `WORKFLOW_CREDENTIAL_REPLACED`。同一 request_id 重试必须可恢复该次结果，保存到机主 DPAPI 保护的短期响应记录，不能再次轮换。并发的不同接续请求检查预期代次，冲突时拒绝，避免两个调用者互相反复夺取。

接续先验证所有者及 request_id 对应的参数摘要，再检查已有幂等响应，最后才校验新的 expected_generation 并轮换；否则响应丢失后的重试会被自己上一次成功轮换拒绝。缓存响应到期或凭证已被更晚一次接续替换时，返回明确过期/已替换状态，不再次轮换，也不把已撤销凭证作为可用凭证返回。

这不能让关机前的活进程跨重启继续；服务重启后仍按现有归属恢复/清理规则处理，不能把历史 command_id 伪装成当前运行进程。

### 多项目与控制通道

资源初始化移出全局注册表锁；锁内完成 STARTING 预留，锁外创建资源，锁内提交或记录失败。初始化过程中关闭服务的分支必须回收刚创建的资源，保持只创建一次。

每个工作流维持生命周期门、在途计数和写操作串行。只读状态、命令输出读取与明确的命令取消经独立控制通道，不等待长轮询。关闭、接续和回收先拒绝新进入，再有限等待在途工作；不能直接删除现有门锁。

控制通道使用明确白名单：工作流/操作状态、已归属命令的输出轮询、已归属命令的取消；不能仅依据工具的 readOnlyHint 决定。write_stdin 含非空输入仍走写串行。空输入轮询会推进输出游标，需要每个命令的短锁，或新增独立绝对游标读取接口；等待输出时不能长期持有该短锁。取消和完成相遇时只返回已观察到的事实，不承诺尚未确认的终止。

控制通道仍执行认证、命令归属、生命周期进入检查和在途计数；取消保留 request_id 幂等。有限等待超时后保留可重试的关闭/清理状态，不删除尚被在途请求持有的资源、门锁或回调记录。

公开实际资源用量、排队原因、所在项目及等待时间。不同项目可并行；同项目竞争写入、前台键鼠串行等约束继续准确报告。

### B 的验收

- 模拟客户端中断，后台操作只执行一次，迟到结果随后可查询。
- 受控操作恰好在等待期限前后完成时，最终结果不被超时分支覆盖；并行读取命令输出遵循已定义的游标语义。
- 请求同 ID 不同参数被拒绝；跨工作流、跨所有者查询被拒绝。
- 长命令运行中丢失令牌，显式接续后读到原输出，原 PID/command_id 不变。
- 接续响应丢失可用同 request_id 取回，凭证只轮换一次；旧凭证失效。
- A 项目初始化故意阻塞时 B 项目仍可进入和执行；同工作流状态/取消不受长轮询阻塞。
- 接续/取消/完成/关闭/空闲回收的竞态测试无资源泄露或重复写入。

## C：安装、升级与完整验收（目标 0.1.6）

便携包自带自启动管理，GUI/CLI 均可启用或取消“登录后连接”。清晰显示正在运行版本、待启用版本与是否需要刷新客户端操作目录；后台服务运行时 GUI 能读取其状态，不能显示另一个未启动对象的状态造成误导。

升级先校验 manifest 和预期版本，使用独立端口/目录完成本地启动检查，再变更下次登录目标；保留上一个验证通过的包和任务定义。校验失败不替换目标。正式发布先源码测试与协议检查，再干净打包，再安装包测试、真实插件验收，最后更新运行说明。私有配置和密钥始终留在本机数据目录。

完善面向 AI 调用者的简短恢复手册：如何选择具体项目、区分等候超时与命令寿命、查状态、接续、结束工作。优先返回机器可判定的下一步，避免含糊的 EXECUTION_ERROR 或建议无条件换对话。

C 的验收：独立目录和干净用户数据配置可注册自启动；损坏包无法覆盖现有目标；变更自启动不打断现有项目；真实插件工具目录与服务端一致；公开 ZIP/源码不含本机配置、凭证、状态和测试数据。第二台物理机只有实际验证后才记通过。

## 执行与发布规则

批准后按 A → B → C 实施；A 中隧道监督与 BF 内部连接可独立并行开发，公共健康契约由主代理统一。每项先写能复现缺口的失败测试，再实现，通过后独立审查。B 的凭证与锁改造由同一实现任务统筹，不能由两个代理同时修改注册表逻辑。

每个版本都执行完整 tests_personal + tests_bf、Ruff、HTTP/schema 兼容与包检查。故障注入只针对本轮创建的进程/配置/数据库。参考 Inspector 的独立客户端验收，但只在确认版本与当前协议兼容后固定依赖。

本方案中的后台恢复、凭证接续和控制通道是拟开发功能。现有 0.1.3 尚未具备这些能力。用户确认范围后再进入产品代码实施，运行服务切换仍按已有约定处理。
